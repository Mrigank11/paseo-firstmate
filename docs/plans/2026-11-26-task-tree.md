# Task tree: building blocks

Design: the `fm-task-tree` canvas (paths A, B and C). Storage stays JSON behind `bin/fleet`.

## Contract

- A task may carry `parent=<group-id>`. A group is a task with `kind=group` (no crew of its own). A project is the implicit root. No `parent` = a top-level task, rendered and routed exactly as before.
- Depth cap: project > group > task, or project > group > group > task (a node has at most 2 ancestors). A parent must be a live `kind=group` task of the same project; no cycles.
- A group's stage is rolled up from its children (computed, never stored): most urgent child group wins (you, fm, running, blocked, next, parked); done only when every child is done. Counts ride with it.
- Owner of a node = nearest claimed node going up (`state/tasks/<id>/claim.json`, a second mate), then the project claim, then the checkout claim. Wakes, comments and the enforcer all use that lookup. A stalled second mate escalates one level up before it reaches the captain.
- Asks stay on their leaf and in the flat Needs you list.
- Second mate: a non-leaf agent that owns one group's subtree. Status goes up through scripts (`bin/fleet rollup`, the finish gate), never through its chat. Its `bin/fleet` writes are refused outside its subtree (`PASEO_AGENT_ID` = the claim). Only the first mate releases it (`bin/fleet release-node`, refused for the claim's own agent).
- Group canvas: a second-mate group shows the second mate's live canvas (it carries `fm.task=<group>`); any group has a generated card (`bin/fleet group-card`) rebuilt from its children, or a hand-written one (`bin/fleet card`).
