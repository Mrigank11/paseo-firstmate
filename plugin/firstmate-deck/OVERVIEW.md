First mate deck gives each project run by a paseo-firstmate first mate a live project page in Lavish. The page shows that project's tasks, what needs the captain, what is running, and the project's notes. Comments the captain makes on the page reach the first mate within about a second, and its replies come back in the page's conversation panel.

## How it works

The plugin reads the first mate's state (`state/fleet.json`, its archive, and `state/projects/<project>/`) and renders each project's page whenever that state changes or a crew agent's status changes. It owns the page's Lavish comment poll, saves each comment to `state/projects/<project>/inbox.jsonl`, and delivers it to the first mate through the Paseo SDK handle the plugin holds (steering it into the current turn when the first mate is busy). The `paseo` CLI is only a fallback for the cold start, before the first SDK handle exists. The plugin never writes the task list; the first mate stays its only writer, through `bin/fleet` and `bin/page`.

In the Paseo app it adds a "Project pages" sidebar row (with a needs-you badge only when something waits on the captain) that opens a screen with one card per active project, each linking to its page, a Project page workspace panel, and a card in the first mate's chat for each batch of page comments.

## Setup

Run `bin/page install` in the paseo-firstmate checkout: it checks Node 22.18+, `jq` and `paseo`, installs the runtime dependencies here (`npm ci --omit=dev`, or `npm install --omit=dev` without a lockfile; `bin/page install --dev` adds the dev dependencies for typechecking), writes `<paseo home>/plugin-settings/firstmate-deck/deck.json` with this checkout as `firstmateRoot`, and installs (or reloads) the plugin. Plugins must be enabled on the daemon (Paseo Settings → Plugins). It also needs the `lavish-axi` CLI, which the plugin finds on the daemon's PATH, in the npx cache, or through `LAVISH_AXI_BIN`.

- `firstmateRoot` can also come from the daemon's `FIRSTMATE_ROOT` environment variable. `~` and symlinks are resolved; a root with no `state/` is reported in the app and the log instead of idling silently.
- Which agent is the first mate is an explicit fact, never a guess: each page's first mate runs `bin/page claim <project>` in its own session (`bin/page start` does it for a new page), which writes `state/projects/<project>/claim.json`. A page's comments go to that agent if it still exists, is not archived and is not crew; otherwise to the checkout-wide claim in `state/firstmate.json` (plain `bin/page claim`; also what every page uses in a checkout from before per-page claims); otherwise to the newest live agent labelled `firstmate=true` that fleet.json does not list as crew; otherwise the comments are queued and that page's banner says "No first mate claimed this checkout". Two sessions can therefore run two pages, each receiving only its own.
- `lavishPort` and `lavishStateDir` default to Lavish's own defaults. The plugin writes the values it actually uses (and its `firstmateRoot`) into each project's `page.json`, and `bin/page` uses those, so the two always talk to the same Lavish.
- `lavishBin` (settings only, default empty) is the absolute path of a `lavish-axi` `dist/cli.mjs` to run instead of the `LAVISH_AXI_BIN` / PATH / npx-cache lookup, e.g. a local fork. Changing it restarts the page polls; no Paseo restart. A path that does not exist is an error on the page's listener, not a silent fallback. `bin/page` does not read it.
- Each poll runs through a small wrapper whose source is embedded in the plugin and run with `node -e` (Paseo bundles the plugin, so there is no sibling file, and nothing is written to `/tmp`). It kills the poll when the plugin dies, so a crashed plugin cannot leave an orphan holding the Lavish listener. Its command line carries the marker argument `--firstmate-deck-poll-wrapper`, which is how a stale poll from an earlier run is recognised and cleaned up.
- A task's asks are addressed by their stable ids (`a1`, `a2`, ...) from `bin/fleet`: comment targets (`t-<task>#a2`), page element ids and option clicks all carry the id, so answering one ask never moves another. A click on an ask that is no longer open (or on an option it does not offer) is recorded as `stale`, relayed as "ignored", and never shown as a pick.
- If `fleet.json` is empty or malformed, the page keeps the last good view, shows "Task state could not be read (fleet.json): showing the last good view", and records `loadError` in `page.json`; `bin/page status` shows it and `bin/page heal` does not reload the plugin for it. A malformed line in `fleet-archive.jsonl` is skipped with a logged count.

## Limits

- If the plugin process is killed outright, Paseo does not restart it. `bin/page heal` reloads it, and the first mate's heartbeat runs that. Meanwhile the page itself shows "This page stopped updating" once the data it polls has not changed for 60 s. That is measured on the browser's own clock (each render carries a growing sequence number and the plugin re-renders at least every 20 s), so a phone whose clock disagrees with the daemon's neither raises a false alarm nor hides a real stall.
- Paseo's phone layout cannot open plugin workspace panels. The sidebar row and its screen work on phones.
- The chat card for page comments appears only after the plugin has seen at least one Paseo event since it started. Comment delivery does not depend on this.

## Task navigator

Every project page has a task navigator, reachable from anywhere on the page. On a screen 640 px or wider it is a fixed left rail. Folded, it is a 48 px spine with one icon per stage and a count bubble (Needs you solid orange); hovering or tapping an icon flies out that stage's titles. Unfolded, it lists every stage's titles, and it pushes the page at 1200 px and up or overlays it below that. On a phone it is a bar under the sticky nav, with the stage counts and the first title that needs the captain; tapping the bar drops down the full list. A title jumps to its card, opening a collapsed group on the way, and the card in view is marked in the navigator. The stages are the page's own groups, in the same order (`GROUPS` in `server/render.ts`; a new group needs only an icon in `STAGE_ICON`, from the Lucide set in `server/icons.ts`). Stages over 7 tasks show 5 and an "N more" button. Clicking a stage heading collapses its titles. The focus button (on the spine, in the rail header and in the phone list) turns on a focus view: the page shows only the task last picked in the navigator, under a "Focus view: <title> · Show all tasks" bar. The fold choice, collapsed stages, focus view and the focused task are kept with the page's open/closed sections (`tn-exp`, `tn-c-<stage>`, `tn-focus`, `tn-sel:<card id>` in `ui-state.json`), so it survives a reload inside Lavish, where the sandboxed page cannot use localStorage. Its containers carry `data-lavish-action`, so its titles stay clickable in Lavish's annotate mode.

## Browser tab and "new" dots

- The live payload carries a hidden `data-attn` block: the Needs-you count (the same number as the sidebar row), one attention key per task (`t-<id>`) and one for the page, and the keys the captain last saw. A key moves when the task's stage group, failed flag, open asks, card text or first-mate replies change; step churn, canvas progress and the refresh stamp do not move it (`server/attention.ts`).
- The page script sets the tab through `window.lavish.setDocumentMeta({ title, icon })` when the Lavish serving the page has it (stock Lavish does not: then only the dots work). Title: `(N) * <project title>`, `(N)` = Needs you, `*` = something changed since last viewed; the favicon carries the same count and a blue dot; `\u26a0` and a grey glyph when the page has not updated for 60 s. It travels in the live update, never in `page.html`.
- "Seen" is `s: { at, keys }` in `ui-state.json`, shared by every browser: a visible tab marks what it showed as seen after 3 s; the newest `at` wins. The first render of a page seeds it, so nothing is new at first. Changed cards and navigator rows get a small "new" dot until seen.

## Read marks, ordering, stop

- The plugin serves a small CORS endpoint (`readMarksPort`, default 4398; `readMarksHost` is the tailnet fallback) for the page's "Done, unread" marks, stored in `state/projects/<p>/ui-state.json`. It never writes `fleet.json`.
- A task's optional `order` sorts it within its group; `provider` labels it when Paseo has no record of its agent; project.json `collapsedSections`, `sectionSubtitles` and `archiveLimit` shape long hand-written pages. `bin/page stop`/`start` pause and resume one page. See `docs/STATE.md`, "Read marks, ordering and long pages".

## The crew's canvas in the card

Each live task card shows its agent's agent-canvas canvas: verdict, BLUF, a steps strip with the Now row, and an "Open canvas ↗" link (no iframe: Lavish's sandbox makes it cross-origin). The deck pulls it itself, on loopback, from agent-canvas's `/api/fm/{summary,card,css}` (`server/canvas-port.ts`): every ~3 s while a page tracks an agent, a card fetched only when its `rev` moved, backoff while the canvas is unreachable. Unreachable or `canvasUrl` = `off` means a small "canvas unavailable" badge and the old card; nothing blocks. The full embed card sits in a collapsed "Full canvas" fold under the compact fragment (the focus view opens it and hides the compact one). In Needs you the card shows the crew's whole canvas open instead (verdict row, then the full card with its BLUF uncut, no compact strip): a strict crew's canvas is short and structured by then. The finish gate adds one bounce: a crew dispatched with `canvas.strict=on` that ends `BLOCKED: canvas ask <id>` with no such open question on its canvas is sent back once with agent-canvas's last refusal (`lastRejection` of `/api/fm/summary`), logged as `bounced`, not put in Needs you and no wake (`server/gate.ts`); the second time it is a normal BLOCKED. A done task shows its `state/tasks/<id>/canvas.final.html` snapshot (`bin/page canvas-snapshot`) in an open "Final canvas" fold, set inline like a running canvas (no frame: the frozen status line and title row are dropped, its `.acv`-scoped stylesheet is hoisted once into the live block; a snapshot of an unexpected shape falls back to a sandboxed `srcdoc` frame); `card.md` folds under it as "Card", and is the body as before when there is no snapshot.

Canvas asks feed the stage engine (`computeStage`'s `canvas` input): idle agent + open ask = Needs you, running agent = "Running · N question(s)", a captain pick waiting for the first mate = With the first mate; a Disputed or Stale verdict is a flag. A canvas ask no curated ask mirrors shows raw ("Uncurated · from the crew") with buttons on the normal option-click path (`t-<task>#c-<id>`); the first mate is told it is a canvas ask. A curated ask carrying `ref {kind:"canvas", block}` whose canvas ask is answered or gone is shown "Resolved on canvas" and flagged `ref-closed` (drift: run `bin/fleet answer`). `bin/fleet stage(s)` read the same canvases (`AGENT_CANVAS_URL`, else the `canvasUrl` the deck stamps into `page.json`).

Settings: `canvasUrl` (default `http://127.0.0.1:6790`; isolated is 6791; `off` disables), `canvasDir` (the agent-canvas checkout, for later snippet tooling).

## One stage evaluation, and the enforcer

The deck is the single evaluator of task stages. It evaluates every live task with the page's own inputs (agents by label and their last messages, the crews' canvases, inbox comments) and writes the result, with the **owner** of the next move and the **reason**, to `state/stages.json` on every render and tick; `bin/fleet stage(s)` print that snapshot when it is fresh (and say "degraded" when they have to compute locally), so the CLI, the page and the sidebar cannot disagree. `docs/STATE.md`, "Computed stage", has the rules.

On top of it the plugin keeps one invariant: **if the first mate is idle, no task is "with the first mate".** When the owning first mate (the project claim, else the checkout claim) is idle after a turn and the snapshot still lists tasks whose next move is its, the plugin sends one `## With you · <project>` digest (task, why, how it clears). Each item gets two reminders at most, the second after 30 minutes; when the second one's turn ends with the item unchanged, the task shows as **Needs you · first mate stalled** (page, `stages.json`, sidebar count). No live first mate stalls a task at once. An idle crew that ended without `DONE:`/`BLOCKED:` gets one reminder first. The crew-finish wake (`## Crew DONE · <task>`) is on by default and goes to the same owner. State is in `state/enforcer.json`; `enforcer: off` or `notify: off` in `state/decisions.md` switch the enforcer or the wake off. The daemon environment variables `FM_ENFORCER_SETTLE_MS`, `FM_ENFORCER_GAP_MS` and `FM_ENFORCER_TICK_MS` shorten the timings (the isolated demo does).
